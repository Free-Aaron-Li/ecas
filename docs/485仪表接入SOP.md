## 一、适用范围
任何 **RS-485 / Modbus RTU** 现场仪表接入（浓度计、流量计、皮带秤、泵状态等），以及**模拟量仪表**（4-20mA / 0-20mA）经 AI 模块的接入。

## 二、标准链路

**A. 数字型仪表（485 直读）**
```
仪表(从机) → A/B 屏蔽双绞线 → DTU(串口服务器) 或 USB-485 → 网络 → 上位机(ECAS)
```

**B. 模拟型仪表（本项目实际走法）**
```
仪表(仅出电流) → I+/I− → AI采集模块(Modbus从站) → A/B → DTU(轮询主站) → 4G → 云/中控
```

## 三、接线规范
| 项 | 规范 |
|---|---|
| 仪表侧（485） | 485+ (A) → 对端 A；485- (B) → 对端 B |
| 仪表侧（模拟） | 电流 **I+ / I−**（注意极性；电流环**串联**） |
| 线材 | **屏蔽双绞线**；屏蔽层**单端接地** |
| 供电 | 按厂家标注极性（如"左正右负"），24V 常见 |
| 终端电阻 | 长距离（>100m）或多机并联时加 **120Ω** |

## 四、必须对齐的参数（差一项即不通）
| 参数 | 仪表 | DTU | 上位机/ECAS |
|---|---|---|---|
| 波特率 / 数据位 / 停止位 / 校验 | ✓ | ✓ | — |
| 从站地址（Modbus ID） | ✓ | — | ✓ |
| 协议（Modbus RTU / 自定义） | ✓ | 透明 或 网关 | ✓ |
| 寄存器地址 + 功能码 | — | — | ✓ |

> ⚠️ **DTU 串口侧参数必须与仪表完全一致** —— 这是"网络通了但读不到数据"的头号原因。

## 五、排错顺序（**隔离法**：先切段，再逐项）
1. **切成四段**：① 仪表本体 → ② 485 链路 → ③ DTU/网络 → ④ 上位机软件
2. **关键隔离手段**：**USB-RS485 转换器 + 串口助手直连仪表**
   - ✅ 能读到 → 问题在 ③ 或 ④
   - ❌ 读不到 → 问题在 ① 或 ②
3. **AI 模块场景追加一步**：先用**厂商测试软件**单独验证模块 → 通了再接 DTU（一步只动一个变量）
4. **高频原因排序**
   | 序 | 原因 | 检查 |
   |---|---|---|
   | a | **A/B 接反** | 对调试一次（485 最经典坑） |
   | b | 端子松动/未压紧 | 逐一紧固 |
   | c | 仪表与 DTU 参数不一致 | 逐项对照表四 |
   | d | **波特率不符** | 两边都要 9600（本项目默认值一致） |
   | e | DTU 非 485 型 / 模式不匹配 | 确认 485 型号；透传 ↔ 轮询模式选对 |
   | f | 仪表**通信功能默认关闭** | 进菜单开启 |
   | g | 寄存器地址/功能码错误 | 查协议表 |

## 六、工具清单
- **USB-RS485 转换器**（隔离必备）
- 串口调试助手 / **Modbus Poll** / QModMaster
- 各设备**厂商专用测试软件**：
  - 中盛 AI 模块 → **中盛综合测试系统**（手册 3.2 节下载）
  - 塔石 DTU → 塔石配置软件
- 万用表（测 485 A-B 差分电压：空闲应 **>200mV**；量电流须**串联**）
- 网线测线仪、`ping` / `telnet`（测 DTU 网络口）

## 七、⚠️ HART ≠ RS485（必须区分）
| | HART | RS485 / Modbus |
|---|---|---|
| 物理层 | 叠加在 **4-20mA 电流环**上的 FSK 信号 | 独立 **A/B 差分总线** |
| 读取工具 | 需 **HART Modem** + 点表 | 串口助手 / Modbus 工具 |
| 与串口助手兼容 | ❌ 读不了 | ✅ 可读 |
| 接 TTL→485 转换板 | ❌ **不可**（电流环 ≠ TTL 串口，硬接会烧板） | — |

> 看到仪表标注"**4-20mA（带 HART）**"，先确认**是否另有独立 485 口**再动手。
> **本项目结论**：只想读模拟量数值 → 接 AI 模块即可，**不需要 HART Modem**。

### 案例 1：DPRO-66 环保型密（浓）度计 —— **已定案**（2026-09-16 起，09-18 定案）

- **菜单入口**：`OK` + `↑` 同按 3 秒

#### 🔍 根因（09-18 澄清，之前的失败原因）
| 端口 | 输出什么 |
|---|---|
| 供电端口 | 设备自身供电（→ 模拟输出为**有源**） |
| **HART 两个端口** | ⭐ **浓度值**（计算后的结果） |
| 其他端口 | **设备原始数据**（伽马**计数率 cps**）+ 供电 |

> ❗ **"从另一路 485 读浓度值"一直不成功 —— 不是配置问题，是那个 485 口里根本没有浓度值**（只有原始计数率）。浓度值只从 HART 端口输出。

#### 🔬 09-25 实测记录（中盛综合测试系统 + USB-485）

**结论：AI 模块方案已跑通；HART 端口确实输出直流电流，无需 HART Modem。**

- ❌ **「只有发没有收」的根因 = COM 口选错**（软件选 COM3，实际模块在 **COM5**）
  → 教训：软件显示「连接成功」只代表串口被打开，**不代表对面有人应答**；先做「拔插法」认口
- ✅ **抓到的收帧（站号1 / 9600 / 8-N-1 / 功能码 04H）**：
  ```
  →发 01 04 00 00 00 12 70 07
  ←收 01 04 24 32 87 00 00 …(00×34)… 4E 54
  ```
  CRC 已独立验算一致（`4E 54`）。`0x3287 = 12935` → **12.935 mA**
- ✅ **寄存器映射实测定案**：功能码 **04H**，**起始 0000H = 通道 1**，寄存器值 **÷1000 = 电流(mA)**
  （18 路模块按 0000H~0011H 连续排列；回帧长度 `0x24`=36 字节 = 18 个寄存器）
- ✅ **量程 = 4-20mA**（09-25 现场确认）：浓度计显示 ≈56.612，模块读 12.935mA；

#### 📜 09-25 历史定案：加性偏移 +0.5 个浓度点（数字已被 09-26 修订取代）

> ✅ **先生原话：「例如换算过来的浓度值是 52.345%，那么实际补偿值是 52.845%，多加 0.5%，而不是 ×1.005」**
> ⇒ **不是乘性百分比，是加性偏移**：在**换算出的浓度**上直接**加 0.5 个浓度点**。
> ⇒ `mA = raw/1000` 与 `未补偿 = (raw − 4000)/160` 均**不变**（先生原话「电流读数不变，浓度换算不变」）。

```
未补偿 = (raw - 4000) / 160        # 中间量，仅作溯源
浓度   = 未补偿 + 0.3              # ⭐ 09-26 现役；09-25 曾为 +0.5（见上节）
```

| raw | 未补偿 | 最终浓度 | 说明 |
|---|---|---|---|
| 12333 | 52.081 | **52.581** | 09-25 21:23 现场读到的原值 |
| 12935 | 55.844 | **56.344** | 与浓度计 56.612 只差 −0.27（比 ×1.005 的 −0.49 更贴） |
| 12935（09-26 口径） | 55.844 | **56.144** | ⭐ 先按 09-26 的 +0.3 算（与 +0.5 只差 0.2） |

⚠️ **为什么 `×1.005` 是错的**：`x × 1.005 = x + x×0.5%`，在 52.345 上只有 **+0.262**，不是 +0.5。
先生说的「0.5%」= **满量程 0~100 的 0.5%** = **0.5 个浓度点**（绝对值），**不是读数的 0.5%**。
⇒ 物理上这是**加性偏置**（零点/标定偏差），不是增益误差 —— 与「模块读数偏低约 0.5 个点」的现象一致。

**两个旋钮（脚本 / 换算器都已实现）**：

```
浓度 = 未补偿 × 系数 + 偏移        # 系数 gain 默认 1.0，偏移 offset 默认 +0.3（09-26 起）
```

```bash
./dpro66_monitor.sh                # 默认：浓度 = 未补偿 + 0.3（09-26 定案；09-25 曾为 +0.5）
./dpro66_monitor.sh -o 0           # 关闭修正，只看未补偿
./dpro66_monitor.sh -o 0.5         # 试别的偏移（例如临时回到 09-25 的 0.5）
./dpro66_monitor.sh -g 1.005       # 若哪天真要乘性修正（一般不用）
```

> 该实现**已于 09-25 深夜移除**，改为上面的「系数 + 偏移」两个旋钮。

#### 📜 历史归档（已废弃，勿照此实现）：当时「三种口径」的讨论

先生当时指出：补偿应当是「**加上 0.5%**」，不是我一直在写的「×1.005」。

**先澄清数学**：`x × 1.005` 与 `x + x × 0.5%` 是**同一个算式** —— 在**同一个量**上，两种说法算出的数完全一样。
⇒ 这句话真正在说的是「**0.5% 加在哪个量上**」，而这一层确实会改变结果。

以现场实测 `raw = 12935`（12.935 mA）为例，浓度计本体读数 **56.612**：

| 口径 | 算式 | 修正后电流 | 修正后浓度 | 与浓度计差 | 物理含义 |
|---|---|---|---|---|---|
| ① 加在读数（电流）上（❌ 未采用） | `mA×1.005` 后再解浓度 | 12.9997 | 56.248 | −0.36 | 误差若来自模块的电流测量；**但会改变显示的电流读数** |
| ② 曾经误当成「定案」：加在浓度上（❌ **已废弃**） | `浓度 × 1.005` | 12.935（不变） | 56.123 | −0.49 | ⚠️ 只有 +0.262，**不是先生要的 +0.5** |
| ③ **加 0.5% 满量程 = +0.5 个点** | `浓度 + 0.5` | 13.015 | **56.344** | −0.27 | ✅ **这才是先生要的**（加性偏移），即上面的最终定案 |

⭐ 三者相差不到 **0.23 个浓度点**，比「4mA/20mA 端点假设错」造成的影响小得多 ⇒ **不必在此过度纠结**；真要一次修干净，仍靠**两点标定**。

**📌 ECAS 侧换算实现的最终口径**（照此写，别再纠结）：
```
mA        = raw / 1000                # 展示用，不参与修正
未补偿     = (raw - 4000) / 160        # 与 mA 严格对应，不参与修正；只作溯源用
浓度       = 未补偿 + 0.3              # ← ⭐ 09-26 现役（屏幕「浓度」列 = 这一步）

#### 📶 DTU 接入步骤（塔石 TAS-KS-301｜09-25 夜）

**① ⛔ 先把 PC 的 USB-485 拔掉**
RS485 是**单主站**总线。中盛软件（PC）和塔石 DTU **都是主站**，同时轮询会互相撞帧
（现象：两边都时好时坏、偶发丢包、值卡住）。**接 DTU 前必须断开 USB-485。**

**② 接线**：DTU 的 `A`/`B` **并联**到模块的 `A`/`B`（A→A、B→B；接反一般只是不通，可对调）；
DTU 供 **9~24V**；插好 4G 卡与天线。

**③ DTU 串口参数必须与模块逐项一致**（"网络通了但读不到"的头号原因）

| 项 | 值 |
|---|---|
| 波特率 | **9600** |
| 数据位 | **8** |
| 停止位 | **1** |
| 校验 | **无 None** |

**④ 工作模式 = Modbus 轮询（主站）**，轮询字符串**含 CRC、手填**（1 串 = 1 条指令）：
```
01040000000131CA          （不带空格）
01 04 00 00 00 01 31 CA   （带空格，按塔石软件的输入习惯）
```
轮询周期建议 **5~10 秒**（浓度变化慢，不必更快）。

**⑤ 回帧与取值（ECAS 侧解析口径）**
```
01 04 02 32 87 4E 54
│  │  │  └─┬─┘ └─┬─┘
│  │  │    │     └ CRC（DTU 通常剥掉，只上传数据域）
│  │  │    └ 寄存器值，**大端**：0x3287 = 12935
│  │  └ 字节数 = 2
│  └ 功能码
└ 从站地址
```
- **`原始值 = 第 4 字节 × 256 + 第 5 字节`**
- 平台侧数据类型建 **16 位无符号整数（uint16 / Word）**，字节序 **大端 AB**
- ⛔ **不要建成 float** —— 它是整数 `12935`，不是浮点
- ⛔ **不在 DTU / 平台侧做浓度换算** —— 只传原始值（见上文定案）

**⑥ 验收判据**：平台应显示 **≈12935**（一万二千多）

| 平台显示 | 结论 |
|---|---|
| ≈12935 | ✅ 正确 |
| 13332 | ❌ 高低字节颠倒（字节序设成 `BA` / Swap） |
| 一直 0 / 卡住不变 | ❌ 轮询字符串错、从站地址错，或 A-B 接反 |
| 65535 / 无数据 | ❌ 模块没应答 → 先确认**模块 TX/RX 灯闪不闪** |

#### 📐 「上行映射」到底是什么（09-25 实测弹窗 m00402）

❗ **重大更正**：传感器里的「**上行映射**」**不是 Modbus 寄存器地址**，而是**两点线性换算**。

实测「编辑传感器」弹窗字段：
```
* 名称          浓度表HART值_1
* 传感器类型    数值型
* 小数位        3(小数位)
  单位          mA
  排序          1
  选择已有映射   ← 可下拉选之前存过的映射；首次用手填即可
  上行映射  ?   x1  x2  ⇒  y1  y2
  下行映射      x1  x2  ⇒  y1  y2
                              关闭 / 确定
```

含义：**「平台从 Modbus 读到的原始值等于 x1 时显示 y1；等于 x2 时显示 y2」**，中间线性插值。

> `显示值 = y1 + (原始值 − x1) × (y2 − y1) ÷ (x2 − x1)`

⚠️ **寄存器地址（从站 / 功能码 / 偏置 / 数据格式 / 采集周期）不在这个弹窗里** ——
按官方 363-MBRTU 案例，它在 **设备管理 → 该设备 → 「设备连接」→「设置连接」→ 读写指令**（见上「🔌 平台侧设置连接读写指令填法」）。
**两处都要配**：读写指令告诉平台「去哪读」，上行映射告诉平台「读到的数怎么换算成显示值」。

**三条可选口径：**

| 方案 | x1 | x2 | y1 | y2 | 单位 / 小数位 | raw 13117 显示成 |
|---|---|---|---|---|---|---|
| ⭐ **A 原样通过**（符合 09-25 定案：**平台只存原值，换算全在 ECAS**） | 0 | 65535 | 0 | 65535 | `raw` / 0 位 | **13117** |
| B 直接显示 mA | 0 | 20000 | 0 | 20 | `mA` / 3 位 | 13.117 |
| C 直接显示浓度 | 4000 | 20000 | 0 | 100 | `%` 或 `g/L` / 2 位 | 56.98 |
| C+ 直接显示浓度（含 +0.5 个点的修正） | 4000 | 20000 | 0.5 | 100.5 | 同上 | 57.48 |

→ ✅ **推荐方案 A**：与「DTU/平台只传原值、换算后置到 ECAS 侧」的定案一致；
   平台网页上不好看，但 ECAS 网页自己换算即可。
   （若只想让塔石监控中心也好看，可用 C，但那样平台推给 ECAS 的就是换算后的值了。）

⚠️ **下行映射 = 平台写值回设备时用** —— 本项目**只读不写**，留空不配即可。

#### ⚠️ 「目标地址」概念澄清（m00452）

MQTT 是「客户端 → broker」模型，**目标地址 = 由谁来当 broker**，**不是**「塔石的云平台入口」。
- 指向**塔石的 broker** → 数据进了塔石，**没有订阅权限就到不了你手里**（除非塔石给你账号 + 帮你转发）
- 指向**你自己的服务器** → 数据直接进你手里

⭐ **「先用官方地址跑通、后续再换自己的」这个打算在 MQTT 里不成立** —— 数据落在哪完全由 broker 决定，换地址 = 换一条链路，数据不自动搬家。

#### 🔬 实测定性（m00461）：`47.99.152.116:10067` **不是 MQTT broker，是 TCP 回声服务器**

探测方法（纯 Python 标准库，7 秒出结果）：
```python
import socket
CONNECT = bytes.fromhex('100c00044d5154540402003c0000')   # 最精简 MQTT3.1.1 CONNECT
s = socket.create_connection(('47.99.152.116', 10067), timeout=5)
s.sendall(CONNECT); s.settimeout(5)
print(s.recv(64).hex())
```
**实测返回**：`reply = 100c00044d5154540402003c0000` —— **与发出的一模一样**，即**原样回声**。

| 返回 | 判定 |
|---|---|
| `20020000` | ✅ 是 MQTT broker，接受匿名连接 |
| `20020001` / `...02` / `...04` / `...05` | ✅ 是 MQTT broker，但被拒（版本 / ClientId / 账号密码 / 未授权） |
| **回显原包 `100c00044d5154540402003c0000`** | ❌ **不是 broker，是 TCP 回声服务器** ← **本次实测结果** |
| 空 / 超时 | 不是 MQTT（私有协议，或等别的格式） |
| `15 03 03 …` | 该端口要求 TLS |

⭐⭐ **这条结果完整解释了 `+STATUS: 1, MQTT CONNECTED` / `MQTT CLOSED` 的反复抖动**：
DTU 发出 MQTT CONNECT → 对面把它**原样丢回来** → DTU 的 MQTT 状态机被自己的包混淆 → 一会判「连上」、一会判「断开」。

⭐ 行为特征与 **`nc -lk 10067`** 完全一致（我早前正建议过用 netcat 监听该端口以观察 DTU —— 疑似由此遗留的监听进程）。
→ 若该机器可 SSH：`sudo ss -tlnp | grep 10067` 或 `ps aux | grep -i 'nc '` 找出并确认那个进程。

**结论**：`47.99.152.116:10067` 这条路**必须换掉目标地址** —— 它不是 broker，通道-1 的 MQTT 永远连不上。
但**同时证明了**：DTU 的 4G 出网、TCP 连接、MQTT 客户端框架**都是好的**，只差一个**正确的 broker**。

#### 🔧⚠️ 为什么「导入参数」改不了 `DTUPACKET`（09-25 深夜发现）

**现象**：把 `+DTUPACKET: 50,2500` 改成 `50,100` 后「导入参数 + 配置参数 + 重启」，回读还是 `50,2500`。

**根因（我们从 m00733 的写入序列已经看到）**：网页「**配置参数**」只下发它认识的那些指令 ——
```
AT+AUTOSTATUS=3,1 / AT+CACHE=1 / AT+DEVICEID=... / AT+POLL=1,1000,1 /
AT+POLLSTR=n,1,0,"..."（1~20）/ AT+RCMDCLOUDEN=2 / AT+SENDID=1 /
AT+UARTCFG=9600,1,0,0 → AT&W → AT+CFUN=1,1
```
**`AT+DTUPACKET` 不在这个列表里** ⇒ 导入的 txt 里写什么都没人往下发，重启后自然还是 DTU 里的旧值。
⇒ 🔑 **`DTUPACKET` 只能走 AT 通道改**：
```
+++                              （进 AT 模式）
AT+DTUPACKET=50,100
AT+DTUPACKET?                    （回读确认）
AT&W                             （写 flash）
AT+CFUN=1,1                      （重启生效）
ATO                              （回数据模式）
```

**⭐⭐ 反过来说：`50,2500` 这套参数本身「算不通 100 秒」**
若 `DTUPACKET` 的字面意思是「攒够 50 字节，或**最多等 2500 ms** 就发一个包」，那打包机制一旦生效，上传间隔**上限就是 2.5 秒**，不可能出现稳定的 100 秒。
⇒ 观测到的「雷打不动 100 秒」反而说明**打包不是当前的限制项**（或字段单位不是毫秒）。⇒ `DTUPACKET` 仍是嫌疑，但**不是最合理的解释**。

#### 🔴 09-25 夜关键发现（m00756）：数据帧其实一直在来 —— **但值 = 0**

用户在服务器上的订阅日志：
```
20:32:12 | len=1  | hex=51                       ×7   ← 心跳 Q
20:32:53 | len=11 | hex=0000000000050104020000   ×8   ← ⭐ 数据帧！
```
**解码**：
```
00 00 | 00 00 | 00 05 | 01 | 04 | 02 | 00 00
 TID     PID     LEN   从站  FC    2字节    值 = 0
```
= 中盛模块（从站 1）对「读 CH1」的**完全合法应答** ⇒ **链路 100% 通，只是通道 1 的电流 = 0.000 mA**。

⭐⭐ **诊断方向就此转向模拟量侧**：

| 层 | 状态 |
|---|---|
| 浓度计 → 模块（**4~20mA 模拟量**）| 🔴 **0 mA —— 信号根本没上来** |
| 模块 → DTU（485 Modbus RTU）| ✅ 正常应答 |
| DTU → 服务器（4G / MQTT）| ✅ 心跳与数据都在到 |
| 服务器 → 监视脚本 | ✅ 正常 |

- ⭐ **0 mA ≠ 浓度 0**：4~20mA 的**活零（live zero）**规定 **4mA = 测量下限，0mA = 断线 / 仪表失电**。模块报 0 而不是 4 ⇒ **回路断了**，不是浓度降到了 0
- 可能原因（按概率）：① 4~20mA 回路接线松脱/断开（模块端或浓度计端）② 浓度计变送器 TRA-9861 失电、关机、或无输出 ③ 模块 CH1 输入损坏，或线接到了别的通道 ④ 模块配置被误写
- ⚠️ **时间线**：`20:02:36` 还是 12888（55.550）→ `20:32:53` 变成 0。这期间正是用户点「配置参数」（DTU 软重启）并在柜内操作的时候 ⇒ **优先怀疑现场接线被动过**
- 🔧 **验证顺序**：① 万用表 mA 档**串联**进回路量电流（⚠️ **不可并联**）② **拔掉 DTU 的 A/B**（RS485 单主站）后用中盛软件整块读 18 路，看是不是只有 CH1 = 0 ③ 检查浓度计本体是否带电、显示是否正常
- 🎓 **判据沉淀**：**「收到帧但值为 0」和「收不到帧」是两件完全不同的事** —— 前者是模拟量/接线问题，后者才是通信问题。看 485 TX/RX 灯即可区分：TX 闪 + RX 闪 + 值 0 ⇒ 通信没问题，别再折腾 DTU

### 6.5 ⭐⭐ 订阅端会丢帧吗？（09-26 实测：会，且原因在 DTU 侧）

**实测结论（2026-09-26 00:38–00:41）**：
- 停掉 `ecas-monitor` 115 秒 → **期间 DTU 发的那 1~2 帧永久丢失**，重启后不会补回来
- 用独立探针抓到 DTU 的发布 **QoS = 0**（`-F '%I|q%q|%x'` 打出 `q0`）
- ⇒ 根因：**QoS 0 的消息 broker 不保存，订阅端不在线就直接丢弃**（与订阅端的 QoS 无关）

**两层处置**：
1. 订阅端已改为**持久会话**（09-26 起）：`mosquitto_sub … -q 1 -i dpro66-monitor -c`
   - `-i` 固定 ClientId + `-c` 关闭 clean session ⇒ 订阅关系存在 broker 里，重连即恢复
   - ⚠️ **只在 DTU 发布 QoS ≥ 1 时才真正防丢**；QoS 0 时该会话形同虚设
   - 想回到旧行为：`--no-persist`（随机 ClientId + clean session）
2. **要彻底不丢，须把 DTU 侧「主题1」的 QoS 从 0 改成 1**（塔石调试软件 → 通道配置 → 主题1 → qos 下拉）
   - 改完之后：订阅端短暂离线（重启/断网）期间 broker 会为 `dpro66-monitor` 排队；重连后补发
   - 代价：补发的帧**没有原始时间**，会以「重连那一刻」的时间入库（payload 里本来就不带时间戳）

**日常影响**：`systemctl restart ecas-monitor` 会吃掉约 1 帧（= 100 秒数据）；不重启则不受影响。
📌 判据：**「库里出现 100 秒整数倍的间隔」= 订阅端有窗口没接上**（DTU 是稳定 100 秒一发）。

#### ⭐⭐ 陷阱：`Timed out` **不是**认证失败

```bash

两种情况的输出**截然不同**，务必分清：

| 输出 | 含义 |
|---|---|
| `Timed out` | **连上了**（认证通过或匿名放行），只是等待窗口内没有消息 —— 本系统数据 **100 秒一条**，`-W 5` 等不到纯属正常 |
| `Connection error: Connection Refused: not authorised.` | **认证失败**，立刻退出，不等超时 |

⇒ 结论：**用 `mosquitto_sub -C 1 -W <小值>` 测认证一定会误判**。本脚本因此改用 `mosquitto_pub` 发一条自测消息（`-t ecas/selftest`，秒级、不需要等数据）来判定认证；只有显式加 `--sub` 才真的去等一帧数据。

> 🎓 判据固化：**订阅超时 ≠ 认证失败**；认证失败一定有 `not authorised` 字样。

## 八·C、数据库：MQTT 原始值落库（PostgreSQL 16，2026-09-26 建）

> 目标：**DTU 上报的原始值一条不丢地存下来**，后续 ECAS 网页直接查库。
> ⭐ 口径铁律（**2026-09-26 先生定案**）：库里**只存三样 —— 设备型号 `model` ｜ 数据时间 `ts` ｜ 数据原始值 `raw`**。
> `mA` / 浓度 / 补偿系数 / 断线超量程判定 / 设备台账**全部由后端处理，不进数据库**。
> ⇒ 库里**没有** `device` 表、**没有**视图、**没有** payload/source 等留痕列（旧结构 09-26 已迁移删除，数据与 payload 已归档留底）。

### 1. 选型：为什么是 PostgreSQL 16

| 候选 | 结论 | 理由 |
|---|---|---|
| **PostgreSQL 16** ⭐ 采用 | ✅ | OC9 有官方包（EPOL）、单机空闲 RSS 实测 **70.7 MB**、SQL 生态最全、`jsonb`/时区/唯一索引去重都能用 |
| SQLite | 备选 | 零运维、更省内存；但后续网页进程 + 采集进程并发写、多设备扩展、远程查询都受限 |
| MySQL/MariaDB | 不用 | 也能干，但本项目没有任何「必须 MySQL」的既有依赖，语法宽松度反而更容易踩坑 |
| **Apache IoTDB** | 不用（现在） | 单机 = ConfigNode + DataNode **两个 JVM**，2.0.11 起要 **JDK 17**，官方 `MAX_HEAP_SIZE` 默认按整机内存给 ⇒ 在 3.6 GiB 的机器上会被 OOM killer 随机杀（可能杀到 mosquitto 丢数据）。**它的强项（百测点秒级采样 / 端边云断网续传）本项目一条都不占** |
| TDengine 3.x | 不用（现在） | 同上；真该换库的门槛是「几十~上百测点 × 秒级」= **20 台 × 1 秒 ≈ 1.7 亿行/年**，到那步再迁也便宜 |

数据量账：**864 行/天（100 秒一帧）≈ 31.5 万行/年 ≈ 30 MB/年**。

### 2. 口令不落明文：systemd 加密凭据

#### 🔄 换口令的完整动作（本次实战顺序，缺一步就会断数据）

1. **先定版本**：确认 DTU 里到底是哪一版（探测法见 §八·B·4 的判定方法）——**DTU 是唯一不能远程改的一环**
2. 更新 broker 口令文件（**口令走 stdin，不进 argv**）：
   ```bash
   printf '%s\n%s\n' "$PW" "$PW" | ssh ecas 'cp -a /etc/mosquitto/passwd /etc/mosquitto/passwd.bak-$(date +%H%M%S); mosquitto_passwd /etc/mosquitto/passwd ecas'
   ssh ecas 'systemctl reload mosquitto'   # 口令文件改动只需 reload
   ```
   - `mosquitto_passwd` 不带 `-b` 时会用 `getpass()` 交互提问，ssh 无 tty 时**回落到 stdin** ⇒ 口令不出现任何进程的命令行
   - 之后 `chown root:root /etc/mosquitto/passwd && chmod 600`（原属主 `mosquitto:mosquitto` 会让 mosquitto 2.x 打警告：`File /etc/mosquitto/passwd owner is not root. Future versions will refuse to load this file.`；本机 `mosquitto.service` 无 `User=` ⇒ 以 root 运行，root:root 安全）
3. **探测验证**：`mosquitto_pub … -P "$PW"` → `rc=0`；同时 `grep dpro66-01 /var/log/mosquitto/mosquitto.log | tail -1` 应看到 `New client connected … as dpro66-01`
4. 重加密 systemd 凭据（旧密文先 `cp -a` 留底）→ `chmod 600` → `systemctl restart ecas-monitor.service`（broker reload 会让常驻订阅掉线，systemd 会自动拉起）
5. 看数据：`SELECT count(*), max(ts) FROM raw_reading;` 与 `/api/health`（DTU 上报周期 **100 秒**，等 2 分钟再判定）

> 💡 顺序反了会怎样：先重启监视 → 监视用旧口令连 → `not authorised`；先 reload broker → DTU 用旧口令连 → 每 3 秒一次

- ⭐ 状态**四档**（参照 NAMUR NE43，比原来多一档）：`断线 raw<3600` ｜ `偏低 3600≤raw<4000`（活零点以下，多为标定偏差）｜ `正常` ｜ `超量程 raw>20500`
- ⭐ 统计**只算有效区间**（4000~20500）：否则两条 `raw=0` 的断线行会把 24h 均值拖到 51.615、最小值 -24.500（修正后 `n=55 / 有效 53 / 均值 54.487 / 最小 50.875 / 最大 57.788`）
- 只读账号：连接一律 `set_session(readonly=True, autocommit=True)`，参数 `hours` 夹 1~720、`limit` 夹 1~5000

### 6. 日志轮转

`/etc/logrotate.d/ecas` → `/root/ecas/logs/*.log`：`weekly rotate 8 compress delaycompress missingok notifempty copytruncate su root root`

- ⚠️ 必须 `copytruncate`：监视脚本以 `>>` 一直持有文件句柄，默认的 `create` 方式会导致继续写老 inode、日志「消失」
