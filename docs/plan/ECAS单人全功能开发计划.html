01计划判断

可行，但必须接受三个前提

结论：单人 52 周做「全功能」偏满但不失真 —— 前提是 基础设施先行 + 特性开关隔离 + 上层轻量。前 16 周打通骨架与主干，后 36 周按层推进。任何阶段超时，砍 P2（插件数量 / UI 花哨度 / 运维自动化），绝不砍 P0（六条铁律 / 错误处理 / 审计 / 测试 / CI）。

为什么不是 3 个月：设计文档是「架构 + 实现」双份完整规范，含反射编解码、协程管线、双库、审计签名、SCADA 控制、插件化、Qt UI。单人逐项实现，仅 L1–L4 的采集链路就需要约 11 周。3 个月只能到「骨架 + 采集链路可跑」。

最大变量：铁律⑥「契约即接口」+ 铁律④「现代化、拒绝宏黑魔法」意味着本项目必须正面解决 C++26 新特性，无法用旧范式绕开。因此第 0 阶段把编译器验证当成最高优先级，而不是等到第 5 周才踩坑。

关键差距（按优先级）

  • P0代码为零：仓库、构建、CI、特性开关、错误/日志/RAII 基础设施全部从零
  • P0C++26 反射/契约/协程的学习曲线，吃掉首月约 30% 时间
  • P0单人无法并行：任一依赖阻塞即全线阻塞
  • P1范围蔓延：协议插件、SCADA 控制、告警引擎都是深坑
  • P1100+ 并发性能达标（第 13 周压测才能确认）

关键假设（未确认，不成立则改计划）

  • A1 每周稳定 37.5h（5×7.5h）；参考容量 30h，余 7.5h 为缓冲
  • A2 已熟悉 C++20 concepts/ranges/协程，C++26 反射契约为边做边学
  • A3 有 Modbus 从站模拟器或真实设备可用
  • A4 IoTDB 2.0 LTS / PostgreSQL 18 / EMQX 可离线部署
  • A5 2027-09-15 为可接受交付日（已预留 10 天缓冲；计划已整体顺延 4 周）

02技术可行性核验（影响排期的关键结论）

设计文档对 C++26 采用「能用即用、演进有路」策略，但部分主张与实际支持度存在偏差。这些偏差直接改变了第 0 阶段的任务与后续降级分支，因此先核验、先定开关，再写业务代码。

设计文档主张 实际支持状态（2026-08 口径） 对计划的影响
静态反射 std::meta（P2996） GCC 16.1+ 已实现，需 -std=c++26 -freflection；含 members_of / name_of / type_of / 函数参数反射；仍有约 40 个 TODO，P3795 未实现 第 1 周 spike 验证反射可用，第 5 周再落编解码；降级分支必须保留（自研 trait + 代码生成）
契约 Contracts（P2900R14） C++26 已采纳；GCC 16.1+ 通过 -fcontracts 支持 ignore/observe/enforce/quick_enforce；Clang 仅实验分支、MSVC 未支持 第 1 周定编译选项；CI 用 GCC enforce；Clang 对标走降级（assert + ensures 内联函数）
std::expected / Concepts / std::generator / std::jthread / mdspan / ranges GCC 16 / Clang 24 均已完整支持 默认全量采用，不预留降级，第 1 周一次性验证
Modules / import std 偏差点：GCC 16 仍需 -fmodules，C++20 模块支持仍标 experimental 改用「命名空间 + 清晰头文件分层」为主，Modules 列为第 15 周可选优化，不阻塞主干
std::execution / Senders-Receivers（P2300） 偏差最大：C++26 已采纳，但截至 2026 年中 libstdc++/libc++ 尚未交付符合语义的运行时；主流做法用 stdexec 或 Boost.Asio 采用「Asio 适配层 + 自研协程调度器」，第 4 周抽象 IExecutor；stdexec 作可插拔后端，待 libstdc++ 成熟再切换
MQTT/OpenSSL/pugixml/concurrentqueue/Catch2 均为稳定成熟组件，版本号合理 第 2 周一次性完成 Conan 依赖解析 + 编译验证，形成可复现构建
Qt 6.11 + MinGW-w64 + GCC 16.2（Windows） 可行但需统一 MinGW 构建套件；Qt 6 对 C++26 模块支持有限 第 10 周交付 Linux 桌面版 UI；Windows 移植单列第 15 周，可选，不进 DoD
编译器策略「MSVC 暂不考虑」 与实际一致（MSVC 对 C++26 新特性支持明显滞后） 维持原决策；CI 只设 Linux（GCC + Clang）两 job
两个偏差点的处理是本项目成败关键：
① Modules 降级为可选 —— 设计文档把 Modules 列为「默认全量」，但 GCC 16 仍需 -fmodules 且标 experimental。单人项目强行 Modules 化会把大量时间耗在构建系统，收益远低于风险。降级为头文件分层，第 15 周再评估。

② std::execution 改用 Asio + 自研调度器 —— 设计文档多处把 std::execution 当「已可用」写进依赖与启用策略。若第 0 阶段不纠正，第 4 周管线实现时会卡住。计划里 IExecutor 接口在第 4 周冻结，stdexec 作为可插拔后端，P0 功能不依赖它。

08现在就开始：今天下午的第一件事

不要从第 0 阶段的「搭 CI』开始 —— 先做那件 4 小时就能验证假设的事：

  1. 装 GCC 16.2 + Clang 24（若机器没有），确认 -std=c++26 可用。
  2. 写三个各 20 行的最小例：① concepts + std::expected 返回 Result；② std::generator 懒序列；③ 一个最小协程 + Asio。全部跑通。
  3. 写反射最小例：-std=c++26 -freflection 下遍历 struct DataPoint 字段并打印。这一步决定第 5 周能否用反射做编解码 —— 若 GCC 16.2 反射有未实现的边界（P3795 类），今天就能知道，从而让降级分支从第一天就在。
  4. 把结果写进 docs/cpp26_support.md：每个特性的开关取值、限制、降级方案。这份文档是第 0 阶段最重要的一页。

为什么先做这个：设计文档 §1.3 把「能用即用」写成了默认策略，但 §3.2 的特性矩阵本身也承认部分特性「实验→演进」。单人项目最贵的成本是「在第 10 周发现第 1 周就该知道的坑」。4 小时验证，换来 46 周的不确定性清零。
