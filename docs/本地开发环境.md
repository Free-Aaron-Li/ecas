## 1. 边界：不动 C++ 工作区

`ecas` 本体是 CLion + CMake 源码工作区。因此 Web 栈：

- 全部放在 **`web/`** 子目录（`web/backend`、`web/frontend`、`web/scripts`）；
- **不引入任何 `CMakeLists.txt`**，不参与 CMake 构建；
- 端口、库名、依赖都与 C++ 侧无关，互不影响。

### PostgreSQL 本地实例做了什么

1. `brew services restart postgresql@18`（launchd 标签已迁移为 `sh.brew.postgresql@18`）；
2. 在 `/opt/homebrew/var/postgresql@18/postgresql.conf` **末尾追加**（改前已 `.bak-时间戳` 备份）：

   ```
   # ==== ECAS 本地开发（2026-09-26 追加）====
   port = 55432
   listen_addresses = 'localhost'
   ```

3. 建角色与库：

   ```bash
   psql -p 55432 -c "CREATE ROLE ecas LOGIN"        # 无口令（本机 trust）
   createdb -p 55432 -O ecas -E UTF8 ecas_dev
   ```

**认证**：Homebrew 集群的 `pg_hba.conf` 对 `local` / `127.0.0.1` / `::1` 是 **trust**
⇒ 本地开发**无需口令**，所以 `web/backend/app/settings.py` 的 DSN 里**不含任何凭据**，
工作区内也不会出现口令文件。

> 生产/云端是另一套：**scram-sha-256 + `/root/.pgpass` + 只监听 127.0.0.1**（见 SOP §八·D）。

## 3. 数据来源：从云端拉同源快照

本地库不造假数据，直接用现场库的 `pg_dump`：

```bash
# 一次性（首次）
ssh ecas "PGPASSFILE=/root/.pgpass pg_dump -h 127.0.0.1 -U ecas -d ecas \
          --no-owner --no-privileges --clean --if-exists" \
  | psql -X -p 55432 -U ecas -d ecas_dev

# 之后随时刷新（幂等）
bash web/scripts/sync-from-cloud.sh
```

首次拉取结果：**377 行**，`2026-09-25 17:05:22+08` → `2026-09-26 09:27:10+08`，
型号 `DPRO-66`，与云端行数一致（377 = 377）。

> 注意：本地库是**快照**，所以看板头部会显示「无新数据 N 分钟 / 数据新鲜」——
> 这是真实状态（本地没有采集端在写），刷新快照后即恢复。

## 5.1 访问令牌（第 1 步已落地）

- 后端只读环境变量 **`ECAS_AUTH_TOKEN`**：**留空 = 开发模式（不校验）**，启动日志会写明；
  设了就保护 `/api/*` 与 `/ws/readings`（`/healthz`、`/api/auth` 永远开放，供探针用）。
- 三种带法：`Authorization: Bearer <t>` ｜ `?token=<t>`（WebSocket / 直链下载）｜ Cookie `ecas_token`。
- 前端：先问 `/api/auth`，要令牌且本机没有 → 弹「需要访问令牌」；令牌存 `localStorage`，
  顶栏可「清除令牌」。令牌**不会**被发往除本后端以外的任何地方。
- 三个刻意的设计（都是吃过亏之后定的）：
  1. **没设令牌要在启动日志里明说**——现场那次 `allow_anonymous true` 就是「以为开了其实没开」；
  2. **比较按 UTF-8 字节做常量时间比较**——`secrets.compare_digest` 对含非 ASCII 的 `str`
     会抛 `TypeError: comparing strings with non-ASCII characters is not supported`；
  3. **非 ASCII 令牌只能走 `?token=`**——HTTP 请求头与 Cookie 值按协议只能是 ASCII
     （httpx/浏览器在发出前就报错），这条写进了测试。
- 起法（注意用 `.venv/bin/python`，别用 `uv run`：`uv` 要先写 `~/.cache/uv`，
  在某些沙箱/受限环境下会直接失败）：

  ```bash
  cd web/backend
  .venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8080          # 开发模式
  ECAS_AUTH_TOKEN='一串随机串' .venv/bin/python -m uvicorn app.main:app --port 8080  # 开令牌
  ```

## 5.2 报警阈值线 + 导出 CSV（第 2 步已落地）

- 阈值来自 `ECAS_ALARM_LOW` / `ECAS_ALARM_HIGH`，默认 **40.0 / 60.0 —— 是占位值**，
  等工艺给出真实控制范围再改（改环境变量即可，不用改代码）。
- **反解共用一处**：`convert.conc_to_raw()` 把浓度阈值换成 raw 判据
  （`low_raw = 10352`、`high_raw = 13552`，即 `4000 + (conc − 0.3) × 160`），
  后端统计与前端画线用的是同一个数，杜绝「图上画 40、代码判 42」这类漂移。
- 前端：趋势图两条虚线（上限红 `#ef4444`、下限琥珀 `#f59e0b`）+ 可开关；
  KPI 卡越限出标签、统计条出「越限」格、明细表越限行加底色与 `↑越限`/`↓越限`。
  ⚠️ recharts 的 `ReferenceLine` 默认 `ifOverflow="discard"`：报警线落在数据域外会被
  **整个丢掉**（数据只有 41~58 时，40/60 两条线都会消失），必须写 `ifOverflow="extendDomain"`。
- 越限判据只对 `status === '正常'` 的行生效：断线/超量程那行的浓度是**数学外推值**，
  没有物理意义，判断设备异常请看 `status` 列。
- 导出：`GET /api/export.csv?hours&limit`（需令牌），返回 UTF-8 **带 BOM**、
  `\r\n` 行尾、开头 10 行 `#` 注释（型号 / 区间与实际覆盖时间 / 行数 / 口径公式 /
  补偿方式 / 报警上下限与 raw 判据 / 异常阈值 / 「外推值无物理意义」提醒），
  文件名 `ecas_DPRO-66_720h_20260926-0957.csv`，`Cache-Control: no-store`。
  前端那个「导出 CSV」是 `<a download>` —— 浏览器不会给它带 `Authorization` 头，
  所以链接里必须带 `?token=`（`api.ts` 的 `withToken()` 已处理）。
- 两个坑：① 模块级 `TestClient(app)`（不在 `with` 里）与其它用例各自进出 lifespan 会打架，
  报 `psycopg_pool.PoolClosed: the pool 'ecas-pool' is already closed` ⇒ 统一 module-scoped
  `with TestClient(app) as c: yield c`；② 报警反解的手算期望值容易错，正确的是
  `10352/13552`，不是 `10384/13584`（补偿是加性 +0.3，反解要先减掉）。
