## 2. SSH 加固

### 2.1 为什么敢关口令登录

- root 已有 **1** 条 ED25519 公钥（`SHA256:2DznbNarIE9YlfA2OFAP6hyUzytSSB0hwIeDq7tloj0`），
  `jc` / `lighthouse` 两个账号**都没有**公钥（所以 `AllowUsers root` 不影响它们之外的人，也不留后门）；
- ⭐ **网页终端 OrcaTerm 不走 sshd**：`/dev/pts/0` 的父进程不是 sshd，而是
  `bash --noprofile --rcfile /root/.orca_term/bash-integration.sh` ⇒ 改 sshd 配置**不会**把先生锁在网页终端外；
- 最后兜底：腾讯云控制台 **VNC**（用实例口令，与 sshd 无关）。

### 2.2 落地的配置

新建 **`/etc/ssh/sshd_config.d/05-ecas-hardening.conf`**（600）：

```
# ECAS 安全加固（2026-09-26）
# 依据：Mac 侧已装公钥（ED25519，SHA256:2Dzn...loj0），腾讯云 OrcaTerm 不走 sshd，
# 丢失密钥可用控制台 VNC 登录救（用实例口令，与 sshd 无关）。
# ⚠️ sshd_config 是「先出现者生效」，所以本文件命名为 05- 以排在 40/50 之前。
PermitRootLogin prohibit-password
PasswordAuthentication no
KbdInteractiveAuthentication no
AllowUsers root
MaxAuthTries 3
LoginGraceTime 30
GSSAPIAuthentication no
```

**命名 `05-` 是关键**：`/etc/ssh/sshd_config:15` 有 `Include /etc/ssh/sshd_config.d/*.conf`，
且 sshd 对同一选项**先出现者生效**；已有的 `50-cloud-init.conf` 内容正是 `PasswordAuthentication yes`，
所以必须排在它前面，否则加固文件形同废纸。

备份：`/root/ecas/archive/sshd_config.bak-20260926-104002`。

### 2.3 ⭐ 带自动回滚的改配置手法（值得复用）

改 sshd 的恐惧是「改错了自己也进不去」。做法是先挂一个 120 秒后自动撤销的定时器，再 reload：

```bash
systemd-run --on-active=120 --unit=ssh-hardening-rollback --collect \
  /bin/bash -c 'rm -f /etc/ssh/sshd_config.d/05-ecas-hardening.conf && systemctl reload sshd'
systemctl reload sshd
# 然后用一个【全新的】连接验证登录正常
ssh -o BatchMode=yes ecas 'echo KEY_AUTH_OK'
systemctl stop ssh-hardening-rollback.timer        # 验证通过，取消保险
```

第二轮（追加 `GSSAPIAuthentication no`）用同样的 `ssh-hardening-rollback2`，
验证标记 `KEY_AUTH_OK_AFTER_GSSAPI_OFF`。

### 2.4 验证证据

## 3. sshguard（替代 fail2ban）

### 3.1 安装与配置

```bash
dnf install -y sshguard            # 连带装 sshguard-firewalld，但本机没有 firewalld
```

改动两处（备份 `/etc/sshguard.conf.bak-20260926-104124`）：

```
/etc/sshguard.conf
  BACKEND="/usr/libexec/sshguard/sshg-fw-iptables"     # 原为 sshg-fw-firewalld，本机没装 firewalld
  LOGREADER="LANG=C /usr/bin/journalctl -afb -p info -n1 -o cat -t sshd"   # 保持默认

/etc/sshguard.whitelist
  127.0.0.0/8
  ::1/128
```

`systemctl enable --now sshguard` → `active` / `enabled`。默认阈值：同一来源 120 秒内 4 次攻击即封禁。

### 3.2 ⚠️ 一个打包缺陷：它不会自己建链

`/usr/libexec/sshguard/sshg-fw-iptables` 的封禁命令是写死的：

```bash
fw_init()    { run_iptables "-L -n" }                              # ← 只列规则，什么也不建
fw_block()   { run_iptables "-I sshguard -s $1/$3 -j DROP" $2 }    # ← 目标链叫 sshguard
```

`fw_init` 不建 `sshguard` 链、也不加 `INPUT` 跳转 ⇒ 真出现攻击时会报
`iptables: No chain/target/match by that name.`，等于**装了不生效**。用 drop-in 固化：

**`/etc/systemd/system/sshguard.service.d/10-ecas-chain.conf`**

```
# 跳转必须先 -C 探测再插入，否则每次重启都会多加一条重复跳转（-I 会插在链首）。
[Service]
ExecStartPre=-/usr/sbin/iptables -N sshguard
ExecStartPre=/bin/sh -c '/usr/sbin/iptables -C INPUT -j sshguard 2>/dev/null || /usr/sbin/iptables -I INPUT -j sshguard'
ExecStartPre=-/usr/sbin/ip6tables -N sshguard
ExecStartPre=/bin/sh -c '/usr/sbin/ip6tables -C INPUT -j sshguard 2>/dev/null || /usr/sbin/ip6tables -I INPUT -j sshguard'
```

> 第一版写成裸 `-I INPUT -j sshguard`，结果每 `systemctl restart` 就多一条重复跳转
> （实测加到 2 条）—— 已改成 `-C || -I`，连续重启两次复查恒为 1 条。

### 3.3 验证证据

```
$ printf 'block 198.51.100.77 4 32\n' | /usr/libexec/sshguard/sshg-fw-iptables
-N sshguard
-A sshguard -s 198.51.100.77/32 -j DROP
$ printf 'release 198.51.100.77 4 32\n' | /usr/libexec/sshguard/sshg-fw-iptables
（链内规则归零，总规则数回到 843）
```

用的是 **RFC 5737 文档段地址** `198.51.100.77`，不碰任何真实来源 IP。
日志里看到的那 674 条 `dport 22 REJECT` **在 `YJ-FIREWALL-INPUT` 链里**，
是腾讯云镜的历史封禁，与 sshguard 无关（sshguard 的规则落在自己的 `sshguard` 链）。

## 6. 腾讯云安全组实际情况（2026-09-26 由先生导出核对）

服务器自己的 iptables 里几乎没有「放行/拦截业务端口」的规则，真正决定公网能不能碰到的
是**腾讯云安全组**。以下是导出的规则与「实际有没有进程在听」的交叉核对：

| 安全组放行（0.0.0.0/0，::/0） | 实际监听 | 判断 |
|---|---|---|
| TCP 1883（MQTT） | ✅ mosquitto `0.0.0.0:1883` | **必须留**：DTU 走 4G、源 IP 不固定，只能靠认证（已开）+ 后续 TLS |
| TCP 22（SSH） | ✅ sshd `0.0.0.0:22` | **留**：已改成只认密钥 + sshguard。⚠️ **不要按来源 IP 限制**——OrcaTerm 走的入口 IP 不确定，锁错就进不去 |
| TCP 8888（宝塔面板） | ✅ BT-Panel `*:8888` | **建议收口**：见下方三种做法 |
| TCP+UDP 11010 / 12121 / 21212 | ✅ easytier-core / easytier-web | 先生另一个项目，**保持不动**（本次没碰） |
| TCP+UDP 11011 | ✅ easytier-core | 同上 |
| TCP 80 / TCP 443 | ❌ 无任何进程监听 | **可删**：空放行，哪天有进程绑上去就直接公网可见 |
| TCP+UDP 11012（WSS & QUIC） | ❌ 无进程监听 | 同上，可删；若 easytier 之后要用再放 |
| ICMP ALL | — | 拒绝（不影响业务） |

**反向发现**：easytier-core 还在听 `15888` / `41425`（TCP）与 `60397`（UDP），但这三个
**安全组没放行** ⇒ 这些口从公网不通（easytier 目前应是靠 11010 中继工作）。
若哪天 P2P 直连不理想，可以回头核对这三个端口——属于先生另一个项目的范畴。

### 宝塔面板 8888 的三种处理（选一）

1. **推荐：删掉 8888 的放行规则，改走 SSH 隧道**（零暴露，用起来一样）：

   ```bash
   ssh -L 8888:127.0.0.1:8888 ecas
   # 浏览器打开 http://127.0.0.1:8888/   （面板本来也监听在回环可达的位置）
   ```

2. **折中：保留公网但限制来源 IP** —— 安全组里把 `0.0.0.0/0` 改成家里/公司的固定 IP 段；
   风险是家宽 IP 会变，变了就连不上（可用控制台临时加回）。
3. **最小改动**：保留公网，但在面板里打开「面板 SSL + 二次验证」，并把面板入口改成随机路径。

> 顺带一提：本项目的看板 **没有**出现在安全组里（后端只听 `127.0.0.1:8080`），
> 这是刻意设计 —— 看板只能经 SSH 隧道访问，见 [`云端部署.md`](./云端部署.md) §3。

## 7. MQTT over TLS（8883 已就绪，2026-09-26）

### 7.1 做了什么

- **自签 CA + 服务器证书**（`/etc/mosquitto/certs/`，属主 `mosquitto`）：

  | 文件 | 内容 | 说明 |
  |---|---|---|
  | `ca.crt` | 自签根证书 `CN=ECAS-MQTT-CA`（RSA 4096，10 年） | 给 DTU 校验服务器用；**这个要发出去** |
  | `ca.key` | CA 私钥（640） | 以后换/加签证书用，**绝不外发** |
  | `server.crt` | `CN=124.222.122.146`，SAN = `IP:124.222.122.146` / `IP:127.0.0.1` / `DNS:VM-0-13-opencloudos` | broker 用 |
  | `server.key` | 服务器私钥（640） | broker 用 |

- mosquitto 追加 8883 监听，**与 1883 并存**（DTU 还没切过来，明文口是回滚路径）：

  ```conf
  # ==== ECAS 浓度计 MQTT over TLS（09-26 追加）====
  listener 8883
  cafile   /etc/mosquitto/certs/ca.crt
  certfile /etc/mosquitto/certs/server.crt
  keyfile  /etc/mosquitto/certs/server.key
  tls_version tlsv1.2        # 最小版本；1.3 仍可用
  ```

  `allow_anonymous false` 与 `password_file` 是**全局**设置（`per_listener_settings` 用默认的
  false），所以 **8883 同样要求账号密码** —— TLS 管"路上不被看"，口令管"谁能连"，两层都要。

### 7.2 验证证据（2026-09-26 10:53–10:57）

- `ss -ltnp` → `0.0.0.0:1883`（明文，DTU 在用）与 `0.0.0.0:8883`（TLS）同时监听 ✅
- 用 CA 校验服务器证书：`Verify return code: 0 (ok)`；
- 带账号密码在 8883 上收发自测（先后台订阅、再发布）⇒ 订阅端收到 `TLS-OK-10:55:15` ✅
- 反例 1：**明文连 8883** ⇒ `Error: Protocol error`（TLS 口不认明文）
- 反例 2：**TLS 连但不带账号** ⇒ `Connection Refused: not authorised.`（认证仍在生效）
- 反例 3：1883 明文口带账号 ⇒ 正常（DTU 现网未受影响）

### 7.3 ⚠️ 两个踩到的坑（都值得记）

**坑 1：`password_file` 属主是 root，broker 一旦整体 restart 就起不来。**

- 症状：`systemctl restart mosquitto` 失败（`status=13`）；mosquitto 日志
  `Error: Unable to open pwfile "/etc/mosquitto/passwd"`。
- 原因：mosquitto 以 root 启动后会**降权到 `mosquitto` 用户**再读口令文件，而文件是
  `root:root 600`（`mosquitto_passwd` 以 root 运行时的默认结果）。此前一直没炸，是因为改完配置
  用的是 **SIGHUP 热加载**（进程仍以 root 身份持有已打开的文件）；**第一次真正 restart 才暴露**。
- 处置：`chown mosquitto:mosquitto /etc/mosquitto/passwd && chmod 640 /etc/mosquitto/passwd`
- ⚠️ 代价：这次 restart 让 MQTT 断了约 **5 分钟**（10:52:15 → 10:57:15 才恢复）。
  DTU 的 QoS 是 **0**，停机期间的数据**永久丢失**（按约 100 秒节拍，丢了约 2 条）；
  `ecas-monitor` 的订阅端**自动重连**，无需人工干预。
- 🎓 教训：**改 MQTT 配置后，先 `systemctl restart mosquitto` 试一次**（或先在测试口验证），
  别只依赖 SIGHUP —— 热加载会掩盖"重启才现形"的权限问题。

**坑 2：证书 SAN 只写公网 IP，本机自测过不了主机名校验。**

`Error: host name verification failed.` / `certificate verify failed` —— 自测连的是
`127.0.0.1`，而 SAN 里当时只有 `124.222.122.146`。处置：重签证书把 `IP:127.0.0.1` 也写进 SAN，
再 `systemctl reload mosquitto` 热加载（不打断现有连接）。

### 7.5 ⚠️ 卡点：塔石云配置界面疑似没有 SSL 选项（2026-09-26）

**原理先说清**：TLS 是**端到端**的。最后一段（DTU ↔ 服务器）能不能加密，**只取决于 DTU
自己会不会说 TLS** —— 服务器这侧无论怎么配都替代不了它。服务器已就绪（§7），但 DTU 若
不会 TLS，它就永远连不上 8883，这段只能是明文。

**当时的实测状态**：DTU 仍连在明文 1883 上（`10.0.0.13:1883 ← 180.108.106.13:32404`，
ClientID `dpro66-01`，用户 `ecas`）；mosquitto **没有配 ACL**（只有一份 `aclfile.example`），
即"只要通过认证，就能读写任意主题"。

**三条备选路径（按推荐顺序）**：

- **A. 找塔石确认固件能力（零成本，先做）**：MQTT 页面有没有 SSL 开关是一个问题，
  但**很多 DTU 的"TCP 通道"支持 SSL/TLS** —— 若 TCP 支持，我们可以干脆不用 MQTT：
  DTU 用 `TCP + SSL` 透传，服务器侧写一个"TLS + Modbus 主站"的接收端（我们主动轮询
  `01040000000131CA`），效果与 MQTT 相同且全程加密。要向塔石问三件事：
  ① MQTT 是否支持 MQTTS（8883）、要不要上传 CA、有无固件版本要求；
  ② 若不支持，**TCP 透传是否支持 SSL/TLS**；③ 有无固件更新可打开该功能。
- **B. 塔石云当中转**：DTU → 塔石云 → 转发到我们服务器。DTU↔塔石云走塔石的链路，
  塔石云→我们用已就绪的 8883/HTTPS。需要问：云平台的**数据转发/推送是否支持 MQTTS 或
  HTTPS 输出到自建服务器**、是否收费。附带好处：来源可收敛成塔石云的出口 IP（白名单）。
- **C. 暂不改 DTU：明文 + 减损措施**。风险量级要诚实说：4G 链路上被动嗅探门槛很高
  （需在运营商侧抓包），**更现实的风险是口令泄漏后被人冒名发布假数据** —— 所以阶段性的
  重点是"能发现被冒名"，而不是"防止被偷看"。可做：
  1. **配 ACL**：`ecas` 只允许写 `dpro66`、只允许读自己的控制主题（现在完全没有 ACL）；
  2. **换随机长口令**并记录轮换方式（DTU 侧只需改一次）；
  3. **冒名检测**：未知 ClientID、来源 IP 变化、发布节拍异常 ⇒ 落成报警事件，看板可见；
  4. 顺手删掉安全组里 **11012** 那条空放行（TCP+UDP 都无进程监听）。
