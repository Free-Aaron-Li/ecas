# miniapp — 微信小程序端（规划中）

> 状态：**占位目录，尚未开工**（2026-11-09 建立）。目录内暂无可运行代码。

## 定位

面向**现场与管理层**的移动端入口：设备状态总览、实时数据曲线、报警提醒、简单的采集参数查看。
桌面端（`cpp/` 的 Qt UI）与 Web 端（`web/`）已覆盖重度操作；小程序只做**轻量查看与提醒**，不承担组态、配置、批量下发等复杂操作。

## 边界（先定规矩，避免第二套后端）

- **不新建后端**：一律调用 `web/backend` 已有的 REST API（生产经 `https://gateway.xshky.org` 统一入口与认证）。
- **不复制业务口径**：单位换算、报警定级、字段含义只在后端实现；小程序只做展示。
- **认证复用网关账户层**：登录、会话、设备绑定（管理员 1 台 / 普通用户 5 台）由 Cloudflare Worker 网关负责，小程序侧不另立账户体系。
- **共享契约放 `shared/`**：接口字段若需多端对齐，写进 `../shared/`，不在本目录各写一份。

## 技术选型（待定，开工前拍板）

| 方案 | 适用 | 备注 |
|---|---|---|
| 原生小程序（WXML/WXSS/JS） | 只做微信、追求包体与启动速度 | 无跨端复用诉求时首选 |
| Taro（React） | 想复用 Web 端 React 经验与组件 | 编译链更重，需评估构建与调试成本 |
| uni-app（Vue） | 后续要同时出支付宝/抖音小程序或 App | 团队若无 Vue 经验不建议 |

选型判据：**是否只服务微信**、**是否需要复用 `web/frontend` 的组件与类型**、**发布节奏**。拍板后在此写入决策与理由（并同步 `docs/design/`）。

## 验收口径（开工时写入）

- 与 `web/` 共用同一套 API 与同一套错误码；
- 首屏（设备总览）冷启动 ≤ 3 s（4G）；
- 报警提醒走微信订阅消息，不在小程序内自建推送；
- 不引入第二份设备/账户数据模型。
